# BAGGA FITNESS — Android / iOS app

The app and the website are **one codebase**. `src/` holds the sections; the
shell around them is chosen at build time:

| Target  | Command           | Entry shell        | Output     |
| ------- | ----------------- | ------------------ | ---------- |
| Website | `npm run build`   | `src/App.jsx`      | `dist/`    |
| App     | `npm run build:app` | `src/shell/AppShell.jsx` | `dist-app/` |

The website stays a single long scroll. The app splits the same sections across
5 bottom tabs, so no screen is ever long enough to scroll expensively. Twelve of
the website's thirteen sections are shared verbatim — `Section`, `SectionHeading`
and `Reveal` read a shell context and adapt, and nothing is forked. The one
exception is the Home tab, which renders `src/shell/HomeScreen.jsx` in place of
the website's `Hero.jsx`; it reuses the same stats, art and data, but it is a
second surface, so keep the two in step when hero copy or stats change.

The two builds write to **different directories on purpose**. `cap sync` copies
`webDir` (`dist-app`) into the native project verbatim, so an app build must
never overwrite the site build.

## Prerequisites

- Node 20+
- **JDK 17, 21 or 22.** This machine builds with `JAVA_HOME=C:\Program Files\Java\jdk-22`
  and Gradle 8.14.3 / AGP 8.13.0, verified working. JDK 11 is too old for AGP 8;
  JDK 25 needs Gradle 9.x.
- Android SDK with platform 36 and build-tools 36.0.0
- Android Studio only if you want the emulator or the GUI

### The `local.properties` gotcha

Gradle finds the SDK via `ANDROID_HOME`, but on this machine that variable points
at the SDK's `emulator` subdirectory rather than the SDK root, so the build cannot
find `platforms/` or `build-tools/`. `android/local.properties` overrides it:

```
sdk.dir=C:/Users/ssd/AppData/Local/Android/Sdk
```

Use **forward slashes** — a `.properties` file treats a backslash as an escape
character. This file is machine-specific and gitignored; recreate it after a
fresh clone.

### Run `npm run sync` once before touching Gradle

Three things Gradle needs to even *configure* are generated by `cap sync` and
deliberately untracked: `android/app/capacitor.build.gradle` (applied at the
bottom of `android/app/build.gradle`), `android/capacitor-cordova-android-plugins/`
(included by `android/settings.gradle`) and the copied web assets. A fresh clone
therefore cannot run `gradlew` directly — it fails at configuration, not at
compilation. Every npm script here runs `sync` first, so use those; if you want
to open Android Studio or call `gradlew` by hand, run `npm run sync` once first.

## Build

```bash
npm run android:apk
```

Builds the web bundle, syncs it, and produces
`android/app/build/outputs/apk/debug/app-debug.apk`.

Other commands:

```bash
npm run sync            # build:app + cap sync, nothing else
npm run android         # sync, then open Android Studio
npm run android:bundle  # release .aab for Play
npm run dev:app         # app shell in the browser on :5181
npm run assets:android  # regenerate icons and splash from assets/*.svg
```

`npm run dev:app` is the fast loop: the app shell runs in a normal browser, so
DevTools work. Capacitor calls are all guarded by `isNative()` and no-op there.

The gradle scripts invoke `.\gradlew.bat`, with the backslash, deliberately. npm
runs scripts through `cmd.exe` on Windows, and Git Bash exports
`NoDefaultCurrentDirectoryInExePath=1`, which stops `cmd` searching the current
directory — so a bare `gradlew.bat` fails with "not recognized" when npm is
launched from Git Bash, and `./gradlew.bat` fails because `cmd` reads the forward
slash as a switch. The backslash form works in both.

## Testing on an emulator

```bash
# from $ANDROID_HOME/emulator
./emulator.exe -avd Pixel_8 -no-snapshot-load -gpu host -no-boot-anim
adb install -r android/app/build/outputs/apk/debug/app-debug.apk
adb shell am start -W -n com.baggafitness.app/.MainActivity
```

Three things that will waste your time otherwise:

- **Wait much longer than feels necessary before sending input.** A warm start
  measured 6.8s and a cold one 20s on this AVD. Taps sent before the WebView is
  interactive are silently swallowed — they do not queue — which looks exactly
  like a broken tab bar. Screenshot to confirm the screen before tapping.
- **The soft keyboard will not appear** if the AVD has `hw.keyboard = yes` in its
  `config.ini` (the Pixel_8 default). `mInputShown` still reports `true`, so the
  IME looks fine while nothing is drawn. Force it:
  `adb shell settings put secure show_ime_with_hard_keyboard 1`. Note the
  emulator's IME then ignores `inputmode`, showing QWERTY where a real Gboard
  gives a numeric pad — the markup is correct, the emulator is not.
- **"System UI isn't responding"** right after a cold boot is the emulator's own
  SystemUI, not this app. Dismiss it and carry on.

A first-launch cold boot also logs `variations_seed_loader: Seed missing
signature` — a WebView-on-emulator artifact, unrelated to the app.

## Release signing

The release build reads an **optional** `android/keystore.properties`, which is
gitignored:

```
storeFile=C:/keys/bagga-fitness.jks
storePassword=...
keyAlias=bagga
keyPassword=...
```

Generate the key once:

```bash
keytool -genkeypair -v -keystore bagga-fitness.jks -alias bagga -keyalg RSA -keysize 2048 -validity 10000
```

Without that file, `assembleDebug` still works and `bundleRelease` produces an
*unsigned* bundle rather than failing — a fresh clone is never blocked by a
secret it cannot have.

> **Back up the keystore somewhere private and permanent.** Play identifies the
> app by that signature. Lose the keystore and the app can never be updated
> again under the same listing — you would have to publish a new one and every
> user would have to reinstall. Never commit it.

Bump `versionCode` (integer, +1 every upload) and `versionName` (the string users
see) in `android/app/build.gradle` before each release.

## Adding iOS

The code is already iOS-ready — `capacitor.config.json` carries an `ios` block,
the CSS uses `env(safe-area-inset-*)` with `viewport-fit=cover`, and nothing
assumes Android. Both the native project **and the `@capacitor/ios` package** are
missing, and `cap add ios` hard-fails on the missing package before it does
anything, so install it first. On a Mac with Xcode:

```bash
npm i @capacitor/ios
npx cap add ios
npm run assets          # generates iOS icons/splash too
npm run ios
```

Then commit `ios/` the same way `android/` is committed.

Two things that differ on iOS and are already handled:

- `env(safe-area-inset-*)` returns real values on iOS. Android's WebView returns
  `0`, so `capacitor.config.json` sets `adjustMarginsForEdgeToEdge: "auto"` and
  the native layer insets the WebView instead. One CSS rule serves both.
- iOS respects `Keyboard.resize: "none"` the same way; the `--kb` variable and
  `data-kb="1"` attribute drive the tab bar out of the way on both platforms.

## Why `android/` is committed

`npx cap add android` scaffolds the project once. After that `cap sync` only
copies the web build and refreshes plugin references — it never rewrites
`AndroidManifest.xml` or `build.gradle`. Those files carry configuration that is
not derivable from anything else:

- `android:screenOrientation="portrait"` on the activity
- the `<queries>` block (see below)
- `android:usesCleartextTraffic="false"`
- `versionName` / `versionCode`
- the optional release signing hook

Regenerating the project would silently drop all of it. Build outputs,
`local.properties`, the copied web assets and the generated configs are excluded
by `android/.gitignore`, so only the project source is tracked.

### The `<queries>` block is load-bearing

`@capacitor/app-launcher` does not simply fire an intent — `openUrl()` calls
`PackageManager.resolveActivity()` first and **rejects** the call when it returns
`null`. Under Android 11+ package visibility that is exactly what happens to any
intent the app has not declared. Without `<queries>`, every outbound link in the
app (WhatsApp, the phone dialler, email, the map) fails. Declaring an intent
there grants visibility only; it requests no permission.

### Predictive back

`targetSdk` is 36, so predictive back is on by default and the legacy
`onBackPressed()` is no longer called. This is fine: `@capacitor/app` registers
through AndroidX's `OnBackPressedDispatcher`, which bridges to the platform's
`OnBackInvokedDispatcher`. `android:enableOnBackInvokedCallback` is deliberately
left unset.

The back button walks four steps, in `src/native/index.js`:

1. close an open overlay (exercise modal, gallery lightbox)
2. dismiss the keyboard
3. go back a sub-screen, then back a tab
4. at the root, ask once — "Press back again to exit" — then `App.exitApp()`

Overlays are closed by dispatching a synthetic `Escape` `KeyboardEvent` on
`window`. Both overlays already carry `role="dialog"` and close on Escape, so
this needed no component changes.

## Icons and splash

Sources live in `assets/` and are **original hand-authored SVG** — an iron
dumbbell with a lightning bolt punched through it, using the palette already in
`tailwind.config.cjs`. Nothing is derived from anyone else's artwork.

| File                    | Purpose                                          |
| ----------------------- | ------------------------------------------------ |
| `icon.svg`              | legacy square icon + iOS                         |
| `icon-foreground.svg`   | Android adaptive foreground (mark only)          |
| `icon-background.svg`   | Android adaptive background (plate only)         |
| `splash.svg`            | launch screen, 2732×2732                         |
| `splash-dark.svg`       | copy of `splash.svg`; the app has no light theme |

Regenerate with `npm run assets:android` (or `npm run assets` once iOS exists).

Two non-obvious constraints are baked into those files:

- **The splash is cropped hard.** Android scales it `CENTER_CROP`, so on a
  1080×2400 phone only the middle **1229px** of the 2732px width survives.
  Everything sits inside that column; the tagline was clipped on the first pass
  and had to be tightened. Verify any edit by cropping to that window, not by
  looking at the square.
- **`scripts/fix-adaptive-icon.mjs` runs after generation**, wired into the same
  npm script so it cannot be forgotten. `capacitor-assets` wraps both adaptive
  layers in a 16.7% `<inset>`, which stops the background full-bleeding — the
  moment a launcher parallaxes the layers, the mask corners show through as
  transparent straight edges — and shrinks the already-safe-zoned mark a second
  time. The script flattens both layers back to the contract the art was drawn
  against. It fails loudly if the generator's output shape ever changes.

Splash text is set in a system sans (Arial), not the site's Oswald: the splash is
rasterised at build time and cannot load a webfont.

### Optional size trim

The portrait lock means the 12 landscape splash rasters can never be shown —
1,020,986 bytes across those files, roughly 1MB of the APK and of git history.
Deleting `res/drawable-land-*/splash.png` is safe while the activity stays
portrait-only (anything missing falls back to `res/drawable/splash.png`). Not
done by default, because they are regenerated by `npm run assets:android` and the
coupling is easy to forget.

## The 60fps contract

The app never animates anything that triggers layout or paint *on the scroll
path*. Concretely:

- **Nothing on the scroll path animates anything but `opacity` and `transform`.**
  The only paint-property transitions are discrete state changes on tap or
  hover — the tab bar's `color`, the segment pill's border and background, and
  `.lift`'s `border-color` / `box-shadow` on pointer devices. None of them run
  while the page is moving.
- **No `filter: blur()`.** The glow effects use a `.bloom` radial mask instead.
- **`backdrop-filter` is disabled on coarse pointers** — it is the single most
  expensive thing a mobile WebView can be asked to composite per frame.
- **`background-attachment: scroll` on touch.** `fixed` forces a full repaint of
  the backdrop on every scroll frame.
- **Fixed chrome is opaque** and carries `contain: layout paint` +
  `translateZ(0)`, so the header and tab bar are their own compositor layers and
  scrolling never repaints them.
- **`content-visibility: auto`** on the three long card lists (exercises, protein
  foods, gallery). It goes on the **card itself**, never on the `Reveal` wrapper:
  `content-visibility` implies paint containment, and on a wrapper that clips the
  card's own focus ring, hover lift and drop shadow. Exercises and protein foods
  carry a `--cv-h` measured from the real rendered card height so the scrollbar
  does not jump; the gallery does not need one, because its grid rows are fixed
  (`auto-rows-[150px]`).
- **No screen is a nested scroll container** — the document scrolls, which is
  what keeps native momentum and overscroll intact on both platforms. (The
  exercise modal and the feedback preview pane do scroll internally. Both are
  bounded overlays, not the scroll surface.)
- **Scroll listeners are rAF-throttled.** The scroll spy was calling
  `getBoundingClientRect()` 13 times per scroll event, forcing several layout
  flushes per frame; the progress bar re-rendered React on every frame and now
  writes a `transform` directly.
- **Screens stay mounted** behind `display: none` after first visit — skipped by
  layout and paint, so returning to a tab is instant *and* keeps its state.
  Scroll position and the last sub-screen are restored per tab.
- `Reveal` is a pass-through in app mode, so no entrance animation runs at all.

Measured on the heaviest screen: 208 frames over a 5,036px scroll, median
16.6ms, p95 17ms, worst 17.2ms, zero long tasks. That was desktop Chrome at
phone dimensions — treat it as an upper bound.

### What the emulator can and cannot tell you

On a Pixel 8 AVD (1080×2400 @ 420dpi, `-gpu host`, Windows host), 12 synthetic
flings across the Home screen via `adb shell input swipe`:

| | frames | janky | median | p90 | p95 | p99 |
| --- | --- | --- | --- | --- | --- | --- |
| This app | 289 | 12.5% | **29ms** | 53ms | 69ms | 125ms |
| Native Settings list (control) | 204 | 2.9% | **31ms** | 36ms | 38ms | 46ms |

The control is the important row. A stock `RecyclerView` cannot beat 31ms on this
emulator either, so **the host's floor is ~30ms per frame and 60fps is not
measurable here at all** — the app sitting at 29ms means it is at the floor, not
that it is slow. Do not read the medians as a real-device result in either
direction.

What the tail *does* say is that this app spikes where the native list does not
(69ms vs 38ms at p95). Some of that is the measurement: `input swipe` with a
120ms duration is a far harsher fling than a finger, delivering a handful of huge
deltas at maximum velocity. The honest position is that the tail is unverified on
real hardware — re-measure on a mid-range device before claiming 60fps publicly.

Chromium logs `tile memory limits exceeded` a few times during **first paint**
only, and never once during scrolling, so there is no checkerboarding under
motion. Reproduce with:

```bash
adb shell dumpsys gfxinfo com.baggafitness.app reset
# ...scroll...
adb shell dumpsys gfxinfo com.baggafitness.app | grep -E "percentile|Janky"
```

### Startup

Cold first launch after install measured `Displayed ... +20s448ms`, of which
~11s elapsed before Capacitor's own `Starting BridgeActivity` — dex verification,
WebView zygote spin-up and `ProfileInstaller`, none of it this app's code. A warm
restart of the same build was 6.8s. Both are emulator figures; a real device is
far quicker, but the shape holds: nearly all of the wait is before any JS runs,
which is why the splash backstop below is timed from JS start rather than launch.

### The splash backstop

`launchAutoHide` is `false`, so the native splash stays up until something asks
it to go, and `AppShell` does that from an effect once React has painted. An
effect only runs if render got that far, so `src/main.jsx` also:

- catches a rejected `boot()` (the shell chunk failing to load), hides the
  splash, and paints a plain inline-styled "could not start" message; and
- hides the splash unconditionally after 8s, which covers the case `boot()`
  cannot see — React reporting a render error thrown above the error boundary,
  leaving an empty root and an already-resolved promise.

Without those, either failure leaves the splash up over a dead page forever,
which reads as a hang rather than as an error. The native module is imported
dynamically there so the **website** bundle never pulls in `@capacitor/*`.

## Known notes

- `npm audit` reports vulnerabilities in `@capacitor/assets`' dependency chain
  (`tar`, `glob`). It is a **dev** dependency used only to rasterise icons; none
  of it ships in the app. Do not "fix" it with `--force`, which would break the
  generator.
- `loggingBehavior` is `none` and `webContentsDebuggingEnabled` is `false` in
  `capacitor.config.json`. Flip the latter to `true` temporarily if you need to
  inspect the WebView from Chrome DevTools on a device.

## Exercised on the Pixel 8 AVD

Recorded so the next person knows what is actually proven rather than merely
written down:

- All five tabs render, with correct safe-area insets top and bottom, and each
  opens on its own first sub-screen.
- The back button walks all four steps: closes the exercise modal via the
  synthetic Escape and nothing else; dismisses the keyboard without leaving the
  screen; returns sub-screen → tab → Home; and exits only on a **second** press
  inside the 2s window. A slower double-press correctly re-arms instead of
  exiting, so test it with `adb shell "input keyevent 4; input keyevent 4"` in a
  single call — two separate `adb` invocations are far enough apart to miss it.
- With the keyboard up the tab bar hides and the content does **not** reflow,
  which is `Keyboard.resize: "none"` plus `data-kb="1"` behaving as intended.
- `assembleDebug` and `bundleRelease` both succeed with no
  `keystore.properties`, and the resulting `.aab` genuinely carries no signature
  block.
- The shipped APK's manifest was checked with `aapt2` rather than trusted from
  source: portrait lock, all six `<queries>` intents, `usesCleartextTraffic=false`,
  `versionName 1.0.0`, minSdk 24 / targetSdk 36.
- Predictive back is confirmed live, not just by reading plugin source — logcat
  shows `CoreBackPreview: Setting back callback ... mIsAnimationCallback=true`
  for the activity, i.e. the AndroidX dispatcher did bridge to the platform one.

Not yet verified anywhere: frame timing on real hardware, and the whole iOS
project.
